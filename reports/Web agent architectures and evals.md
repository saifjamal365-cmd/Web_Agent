# Shrink the page, then check the cart

In 2025-2026, the best web agents come in two families. The big labs (OpenAI Operator/CUA, Anthropic Claude computer use, Google Gemini 2.5 Computer Use, which powers Project Mariner) run **one model in a loop over screenshots** and click by pixel coordinates, with safety checks running outside the model. Open frameworks (Browser Use, Stagehand on Browserbase, Skyvern, Notte, Playwright MCP) give the model a **trimmed text view of the page**, plus cheap search tools and a **schema-based extract tool**. The biggest measured gains do not come from adding more agent roles. They come from three plain changes. The first is a smaller action menu and a cleaner page view: AgentOccam went from **14.2% to 44.2%** on a WebArena subset this way. The second is site-level tools that replace many clicks: WALT needs **1.3-1.4x fewer steps**. The third is a separate check that the goal really happened: Skyvern's validator added **about 17 points**. Be careful with headline scores. Vendors claim 85-99% on WebVoyager and Online-Mind2Web, but independent runs give about 40-69%. Only three of the eight metrics you asked about (task success, step accuracy and policy compliance) have standard formulas. We must define the other five ourselves. Our agent failed the Amazon laptop task after 39 steps and 374k tokens, or **about 9,600 tokens per step**. That fits the failure causes named in the research: too many tools, full history in the context, filters done by clicking, and no state check on the cart. The top three fixes are: a "search, filter, extract, compare" fast path with a typed extract; a smaller tool menu per step, with only the latest page view kept in history; and a progress ledger with a stall counter and a hard cap of 25-30 steps.

## Two families: pixel agents from the labs, text-tree agents from open source

The frontier labs have mostly agreed on one design: one model, raw pixels, a virtual mouse and keyboard. OpenAI's Computer-Using Agent (Jan 2025) sees **only screenshots** and acts with click, scroll and type, with "no OS- or web-specific APIs" ([OpenAI CUA](https://openai.com/index/computer-using-agent/)). ChatGPT agent (Jul 2025) puts a visual browser, a **text browser**, a terminal and API access behind one model. It does not split them across several agents ([OpenAI ChatGPT agent](https://openai.com/index/introducing-chatgpt-agent/)). Claude computer use works the same way. Claude returns tool calls and the client runs them. Claude can send **several actions in one turn**. The client stops at the first failure, returns `is_error: true`, and marks the rest "Not executed". A `zoom` action lets Claude read small text at full resolution ([Claude computer use docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool)). Gemini 2.5 Computer Use gets the request, a screenshot and **recent action history**. After each action it gets back a new screenshot **plus the current URL**. A per-step safety service outside the model checks each action before it runs ([Google blog](https://blog.google/technology/google-deepmind/gemini-computer-use-model/)). Amazon's Nova Act took a different path. Developers split the workflow into **many small `act()` calls** mixed with normal Python and Playwright code, instead of giving the model one long goal ([TechCrunch](https://techcrunch.com/2025/03/31/amazon-unveils-nova-act-an-ai-agent-that-uses-a-web-browser/)).

Open-source frameworks read the page as text, and they put most of their effort into making that text small. Browser Use 0.x lists only interactive elements as `[index]<type>text</type>`. It marks **new elements with `*[`** and shows mainly the visible part of the page. Its prompt says to use `search_page` and `find_elements` "before scrolling or calling `extract`, since they're free", meaning they use no LLM ([Browser Use system prompt 0.12.0](https://raw.githubusercontent.com/browser-use/browser-use/0.12.0/browser_use/agent/system_prompts/system_prompt.md)). Browser Use 1.0 went further. It **removed all built-in actions**, and the model now writes Python against raw CDP in a persistent REPL ([Browser Use docs](https://docs.browser-use.com/customize/tools/available)). Its team calls code execution "the biggest improvement" in their 2026 benchmark run. They also report that **TSV output instead of JSON saved about 40% of tokens** ([Browser Use Online-Mind2Web post](https://browser-use.com/posts/online-mind2web-benchmark)). Stagehand has four primitives: `act`, `observe`, `extract` (with a Zod or Pydantic schema) and `agent`. It uses "hybrid accessibility-tree trimming", and `observe()` can be limited to one container ([Stagehand README](https://github.com/browserbase/stagehand); [Stagehand caching docs](https://docs.stagehand.dev/v3/best-practices/caching)). Playwright MCP gives element refs from an accessibility snapshot. The snapshot can be limited with `target` and `depth`. `browser_find` is a cheaper text or regex search over it, but there is no LLM extract tool ([Playwright MCP README](https://github.com/microsoft/playwright-mcp)). Agent-E lets the navigator pick one of three DOM views: `text_only`, `input_fields` or `all_fields`. After every action it reports in words what changed on the page ([Agent-E](https://arxiv.org/html/2407.13032)).

Research systems show which page views work. **SeeAct** found that grounding is the bottleneck. In its version 2, set-of-mark prompting "is not effective". The best method combined HTML with visuals, and it still trailed perfect grounding by **20-25 points** ([SeeAct](https://arxiv.org/html/2401.01614v2)). **WebVoyager** used marked screenshots and reached 59.1% on 15 live sites in 2024 ([WebVoyager](https://arxiv.org/abs/2401.13919)). **AgentOccam** shows that a text view built for LLMs wins. It turns tables and lists into Markdown, merges labels into the elements they describe, and keeps only "pivotal" elements in history ([AgentOccam](https://arxiv.org/html/2410.13825)). Our design (a numbered element list, find, extract, and vision only when needed) belongs to the open-source text family. That is the right family for a non-frontier model like gpt-oss-120b, because pixel grounding is where smaller models fail.

## Extra roles help as checkers, not as extra talkers

The clearest role study is Skyvern's. A single prompt in a loop scored **about 45%** on WebVoyager. Adding a Planner, which keeps a memory of done and pending goals, raised it to **68.7%**. Adding a Validator, which checks each goal and reports errors back for re-planning, reached **85.85%**. Skyvern explains why: the actor's own success reports "were not always accurate" because **some clicks failed silently** ([Skyvern 2.0](https://www.skyvern.com/blog/skyvern-2-0-state-of-the-art-web-navigation-with-85-8-on-webvoyager-eval/)). Magentic-One gives the second strong result. Its Orchestrator keeps a **task ledger** (facts, guesses, plan). Every step it also fills in a **progress ledger** with five questions: is the request done, are we looping, are we making progress, who acts next, and with what instruction. If the stall counter reaches 2, it reflects and re-plans. Replacing this with a plain group chat **cut GAIA performance by about 31%** ([Magentic-One](https://arxiv.org/html/2411.04468v1)). Surfer-H also splits policy, localizer and validator. The validator is the hardest part to shrink: a small validator costs **12-16 points** ([Surfer-H](https://arxiv.org/html/2506.02865v2)).

The opposite view is also real. Browser Use 1.0 **removed its planner and memory options** and still made the top self-reported score. It relies on a strong self-check prompt and an external judge instead ([Browser Use migration](https://docs.browser-use.com/open-source/migrating.md)). AgentOccam gets planning with no separate planner: the same LLM adds and prunes branches in a plan tree ([AgentOccam](https://arxiv.org/html/2410.13825)). On pure browsing, single-loop frontier models beat multi-agent research systems. CUA scored 58.1% on WebArena against Magentic-One's 32.8%, although the models and dates differ ([OpenAI CUA](https://openai.com/index/computer-using-agent/)). The best reading is this: **keep one actor loop, add explicit progress state with loop detection, and add a separate validator that looks at real page state**. A planner is worth it only as part of that state. Memory helps when the same sites come back. Agent Workflow Memory gave **+51.1% relative** on WebArena with about 2 fewer steps ([AWM](https://arxiv.org/html/2409.07429v1)). But a 2026 EMNLP paper found that a plain agent given the **same token budget** matched or beat such memory methods ([ACL Anthology](https://aclanthology.org/2026.emnlp-main.1657.pdf)). Self-made skills are often unstable too ([ContractSkill](https://arxiv.org/html/2603.20340v3)).

Recovery patterns repeat across systems. The first is **observe after every action**. Anthropic's docs admit Claude "sometimes assumes an action succeeded without checking" ([Claude docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool)). Gemini returns the URL after each step, and Agent-E describes the change in words. The second is **stop a batch at the first error** and tell the model exactly which actions did not run (Claude). The third is **cap retries**: Browser Use says do not retry a failing action or a blocked URL more than 2-3 times, and to review the plan at 75% of the step budget ([Browser Use prompt](https://raw.githubusercontent.com/browser-use/browser-use/0.12.0/browser_use/agent/system_prompts/system_prompt.md)). The fourth is **detect loops**: one guard stops a run when the same (tool, arguments, result) triple repeats ([OpenClaw](https://docs.openclaw.ai/tools/loop-detection.md)). The fifth is **re-plan on a schedule**: WALT re-plans every 15 steps inside a 30-step budget ([WALT](https://arxiv.org/html/2510.01524v1)). The sixth is **end cleanly**: when the budget runs out, Browser Use gives one "delivery-only" turn to hand in partial results with `success=False` ([Browser Use long tasks](https://docs.browser-use.com/open-source/long-tasks.md)). Human hand-off follows rules more than judgment. Logins, CAPTCHAs and payments always go to the human. Magentic-UI sorts actions into **always ask** (for example, upload), **maybe ask** (an LLM decides, for example a button click) and **never ask** (scroll) ([Magentic-UI](https://arxiv.org/html/2507.22358v1)).

## Benchmarks: 90%+ claims shrink to about 40-70% under independent checks

There are two kinds of benchmark. **Sandboxed** benchmarks check the final site or database state with code. **Live-web** benchmarks need an LLM judge or a human. The live ones are where most headline numbers come from, and they are inflated. On a cleaned, human-annotated WebVoyager, **Operator scored 68.6% against the 87% OpenAI reported**. Browser Use's 89% left out 55 tasks marked "impossible" and only reviewed tasks that the evaluator marked as failures ([Emergence WebVoyager](https://arxiv.org/html/2603.29020)). On Online-Mind2Web, human judges gave Operator 61.3%, Claude CU 3.7 56.3%, Browser Use 30.0% and Agent-E 28.0% in 2025. A search-only agent solved 51% of a WebVoyager sample, which shows that **WebVoyager has shortcuts** ([Online-Mind2Web paper](https://arxiv.org/html/2504.01382v4)). Princeton's HAL ran agents independently and got at most **42.33%** (SeeAct + GPT-5) ([HAL](https://hal.cs.princeton.edu/online_mind2web)). Browser Use now claims **97%** with its own agentic judge ([Browser Use post](https://browser-use.com/posts/online-mind2web-benchmark)). No one has checked that claim independently.

Shopping tasks are where agents break most. **Filter and sort errors were 57.7% of Operator's Online-Mind2Web failures**, and navigation errors were 19.6%. Other agents often claim constraints are met when they are not, repeat actions, stop too early and use keyword search instead of site filters ([Online-Mind2Web](https://arxiv.org/html/2504.01382v4)). Per site, Operator scored 100% on apple.com but only 35% on booking.com ([Emergence](https://arxiv.org/html/2603.29020)). Judges are not neutral either. Changing only the agent's chain-of-thought raised judged success by **19.6-22.9 points** above true success ([Gaming the Judge](https://arxiv.org/html/2601.14691)). The best LLM judges reach only **about 70% precision**. Rule-based checks reach 83.8% precision but miss many real successes ([AgentRewardBench](https://arxiv.org/abs/2504.08942)).

## Only three of the eight metrics have a standard formula

Task success, step accuracy and policy compliance have published formulas. Recovery rate, hallucination rate, tool-call reliability and human intervention rate do not have a standard web-agent definition. We have to define them and cite the closest example. The table gives the accepted definition where it exists, and a working formula for our evals where it does not. The formulas marked "ours" come from the research notes. No paper has published them in this exact form.

| Metric | Accepted definition or closest precedent | Formula we should use |
|---|---|---|
| **Task success** | Share of tasks where code checks of answer and final state pass (WebArena); or where a human or WebJudge says success (Online-Mind2Web) ([WebArena-Verified](https://github.com/ServiceNow/webarena-verified); [OM2W](https://arxiv.org/html/2504.01382v4)). Repeat-run consistency: pass^k from tau-bench ([tau-bench](https://arxiv.org/abs/2406.12045)) | SR = tasks passing a **state check** (cart contents, URL filters, answer) ÷ tasks. Also report pass^3. |
| **Action accuracy** | Mind2Web: Element Accuracy, Operation F1, Step SR (step correct only if element and operation are both right). Always clicking gives >80% Op F1, so use Step SR ([Mind2Web](https://arxiv.org/pdf/2306.06070); [Ponder & Press](https://arxiv.org/pdf/2412.01268)) | Step SR on a small labelled set of our own traces. |
| **Tool-call reliability** | No formal web definition. ST-WebAgentBench flags wrong or invented inputs (`is_input_hallucination`) ([ST-WebAgentBench](https://arxiv.org/html/2410.06703v4)) | Ours: tool calls that parse, run without error and hit the intended element ÷ all tool calls. Track **malformed-call rate** separately. |
| **Recovery rate** | WAREX measures the drop in success when it injects faults ([WAREX](https://arxiv.org/html/2510.03285v1)) | Ours: tasks that hit an error and still succeed ÷ tasks that hit an error. Robustness drop = SR clean − SR with injected pop-ups. |
| **Instruction following** | ST-WebAgentBench CuP = share of tasks completed **with zero policy violations**; CR = completion rate ([ST-WebAgentBench](https://arxiv.org/html/2410.06703v4)) | CuP over all user constraints (price, RAM, brand, "no checkout"). |
| **Hallucination rate** | MIRAGE-Bench: actions unfaithful to the task, history or page ([MIRAGE-Bench](https://arxiv.org/abs/2507.21017v1)). A 2026 preprint defines false success as claim vs state mismatch (we did not check this source) ([preprint](https://arxiv.org/html/2606.09863)) | Ours: **false-success rate** = runs where the agent says done but the state check fails ÷ runs where it says done. |
| **Human intervention rate** | No headline metric. Operator: 92% confirmation recall on risky actions ([Operator card](https://openai.com/index/operator-system-card/)). Magentic-UI: help asked in 10% of tasks ([Magentic-UI](https://arxiv.org/html/2507.22358v1)) | Ours: runs needing human rescue ÷ runs. Count **required confirmations** (good) apart from **rescues** (bad). Also: confirmation recall on risky actions, target 100%. |
| **Execution time** | Online-Mind2Web: steps vs human steps; failures take about **2x the steps** of successes ([OM2W](https://arxiv.org/html/2504.01382v4)). HAL: USD per run ([HAL](https://hal.cs.princeton.edu/online_mind2web)). Wall clock 29-1,370 s per task ([Emergence](https://arxiv.org/html/2603.29020)) | Median seconds, steps, LLM calls and tokens **per successful task**. |

Report steps and tokens per success, not plain averages. AgentOccam's plain agent took the fewest steps (6.2) only because it gave up early, at 14% success ([AgentOccam](https://arxiv.org/html/2410.13825v2)). For reference, Agent-E needed about **25 LLM calls and about 150 s per successful task** ([Agent-E](https://arxiv.org/html/2407.13032)), and Gemini 2.5 Computer Use reported about **225 s** ([Google](https://blog.google/technology/google-deepmind/gemini-computer-use-model/)).

## Why the laptop task took 39 steps, and what to change first

We do not have the step trace in these notes, so the diagnosis below is a reasoned guess. The numbers already say a lot. A task of this shape (search, filter, compare, add to cart) should take **about 6-10 steps** on a good path. Research agents cap it at about 30 steps (WALT uses 30), and pruned page views cost **about 2-3k tokens per step** ([WALT](https://arxiv.org/html/2510.01524v1); [AgentOccam](https://arxiv.org/html/2410.13825v2)). Our run used 39 steps and about 9,600 tokens per step. Failures take about twice the steps of successes ([Online-Mind2Web](https://arxiv.org/html/2504.01382v4)), so a long run is itself a warning sign. Four likely causes fit what the research reports. First, the model sees about 24 web tools plus desktop tools at every step. Second, the history grows with every page view. Third, the price and RAM filters were probably set by clicking widgets, which is the top failure in shopping tasks. Fourth, add-to-cart can fail silently, and only a check of the cart would catch it. There is one more risk that is specific to our stack. gpt-oss-120b sometimes writes a raw Harmony tool call as **plain text after about 5 tool calls**, and in a LangChain/LangGraph graph this can end the run as if it were a final answer ([LangChain forum](https://forum.langchain.com/t/harmony-response-format-sometimes-outputted-when-using-gpt-oss-120b-as-an-agent/2554.md)). Groq users report tool-call errors on both gpt-oss models ([Groq community](https://community.groq.com/t/tool-calling-errors-on-both-gpt-oss-models/406)).

The table ranks changes by expected impact for each unit of work. The impact numbers come from other systems on other benchmarks. They show direction and rough size. They are not promises for Amazon.

Some popular ideas are **not** on the list on purpose. Best-of-N rollouts raise OSWorld from 62.6% to 69.9%, but they need about ten full runs per task ([Agent S3](https://arxiv.org/abs/2510.02250v1)). That makes the token problem worse. A full multi-agent split also adds cost and failure points for short, single-site tasks. Magentic-UI still trails single-loop browsers on WebVoyager (82.2 vs 87.0-89.1) ([Magentic-UI](https://arxiv.org/html/2507.22358v1)). A switch to pixel-only control would remove our main strength. SeeAct shows grounding is the weak point, and gpt-oss has no trained pixel grounding. Keep `look` as the fallback for when the text view fails.

## Conclusion

The research changes the question we should ask. The question is not "which agent roles are we missing?" Our graph already has more roles than Browser Use 1.0 or AgentOccam. The question is "how much does the model have to read and decide at each step?" The systems that improved most in 2025-2026 did it by **taking work away from the LLM**: fewer actions, smaller page views, one schema extract instead of many reads, code for comparing, and code (not the model's word) for deciding that the cart really changed. For a mid-size open model such as gpt-oss-120b, this matters even more than for frontier models. SkillWeaver found that weaker agents gain **40-130% relative** from high-level tools built by stronger ones ([SkillWeaver](https://arxiv.org/abs/2504.07079v1)).

Two cautions follow. First, judge our progress only with state checks on our own tasks. Public headline scores are self-judged and differ by about 18-55 points from independent runs, and LLM judges can be fooled by the agent's own reasoning. Second, our "lessons memory" should hold **concrete, replayable site recipes** (URLs, filter parameters, refs), not free-text advice. The 2026 token-matched results suggest that free-text memory often costs as many tokens as it saves. If ranks 1-5 work as the evidence suggests, the Amazon laptop task should finish in about 10-15 steps and under 150k tokens. That is still an estimate until the eval suite in rank 11 measures it.
